# Quest Escrow composes the Wallet verbs

ADR-0009 keeps money independent of the Quest model. It already permits one narrow, transaction-aware Wallet adapter that takes opaque Wallet identifiers and integer amounts. This decision extends ADR-0009. It does not supersede it. Every new Wallet verb below stays inside that permission. ADR-0009 already carries one exception: the Admin Dispute Case adapter `settleDisputeCase`, in which Wallet owns a balanced correction and its audit projection. This decision leaves that adapter as it is.

Quest Escrow composition lives in one Quest-side module: `src/modules/quest/quest-escrow.service.ts`. It is the only file under `src/modules/quest/**` that knows a Funding Reservation exists. It is the only file under that path that names the `'quest'` caller scope. Its verbs are `readQuestEscrow`, `settleQuestWorkers`, `releaseQuestEscrow`, `questFundingCapacity`, and `platformFeeForQuest`. No file under `src/modules/quest/**` imports a symbol from `src/database/schema/wallet.schema.ts`.

The Wallet gains three read verbs and one predicate. `readFundingReservation` takes an owner, a caller scope, and a caller reference. It returns the Funding Reservation id, status, and remaining amount, or nothing. `fundingCapacityFor` compares the Spending Balance with a required amount. It returns a verdict with a reason. It never creates a Wallet. `platformFeeForReservation` reads the Funding Reservation `policyRevisionId` and applies `calculatePlatformFeeSatang`. It serves only a legacy Quest with no Platform Fee captured at publish. The predicate beside `assertWalletOperationAllowed` lets the capacity verb answer without an exception. These verbs take opaque identifiers and no lock.

Quest owns the Platform Fee read and the allocation arithmetic. Quest sends the fee captured at publish and marks it as a Quest Escrow snapshot. `settleFundingReservation` validates that mark. `quest.platformFeePerWorkerSatang` is the source. A legacy null falls back to `platformFeeForReservation`. Quest deletes its own policy fee read and stops importing the Money Policy revision table. The pure `calculatePlatformFeeSatang` stays a Wallet import, because it reads no table. The inclusive Quest Funding Total search stays Quest publish quoting policy. The four remainder splits stay Quest allocation policy and collapse into one Quest-module helper.

The lock order is one order everywhere. Only mutating Wallet verbs lock. The Funding Reservation row locks first. The Wallet rows lock next, sorted by id. Publish no longer locks the Wallet table first. `reserveSpending` takes the Wallet lock itself.

`releaseFundingReservation` treats a non-ACTIVE Funding Reservation as a no-op. It returns the current state instead of throwing. Quest deletes its release pre-checks, with one exception. `quest-lifecycle.worker.ts` keeps an unlocked `readQuestEscrow` status read, because the worker must report each released Quest exactly once. The idempotent verb cannot answer that question. A replay of a completed release returns the same result as the first release, which the idempotency contract requires. The read takes no lock. The Quest row lock that the worker already holds makes the read correct.

Publish asks `questFundingCapacity` for a verdict. The pure publish policy receives the verdict. It loses the `WalletStatus` type and the `walletStatus` snapshot field. The blocking reasons stay `WALLET_NOT_ACTIVE` and `INSUFFICIENT_SPENDING_BALANCE`. A missing Wallet keeps its current money error at the Quest boundary. Publish never provisions a Wallet. Every mutating Wallet verb returns the remaining Funding Reservation amount after the write. Quest drops its unlocked re-reads of that amount.

The capacity read is advisory, because it takes no lock. `reserveSpending` stays authoritative under its own lock. A debit between the advisory read and the reserve surfaces as a `MoneyDomainError`, not as a blocking reason. This is an accepted trade-off.
