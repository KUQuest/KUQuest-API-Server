# Wallet owns the Money Command protocol

Six money services — funding, wallet credit, conversion, payout, top-up, and release — repeat one acquire-or-replay convention on `wallet_idempotency_keys`, with small local drift between the copies. This decision keeps one implementation of the mechanics in one Wallet-owned module, `src/modules/wallet/wallet.money-command.service.ts`, and `src/modules/wallet/index.ts` exports it. The module exposes three verbs: `runMoneyCommand` acquires the key row or replays a prior result, `stampMoneyCommandResource` stamps the resource pointer on an in-progress row, and `completeMoneyCommand` stamps the pointer and completes the row. A caller passes its transaction, the principal, a `wallet.*` operation scope, the Idempotency-Key, and a hash of its own canonical request bytes; the module never canonicalizes a request and never sees the resource type, because the result type belongs to the caller.

`runMoneyCommand` inserts the key row with the principal, the scope, the key, the `request_hash`, and `expires_at` at `now() + 24 hours`; the insert does nothing on a conflict. The winner runs its `execute` hook inside the caller's transaction. A throw rolls the whole transaction back, and the rollback erases the key row: a rejected command leaves no key row, and a retry with the same key re-executes. The rows store only the `request_hash` and the pointer columns, never request payloads (ADR-0008, ADR-0011). Completion is caller-owned. The caller calls `completeMoneyCommand` in the same transaction or a later one, because a payout completes at prepare while a top-up must stay in progress across the provider call. `expires_at` is write-only: the Server stamps it at insert and never reads it.
A null `resource_type` records the no-op release shape, which completes a key row without a resource pointer.
Top-up splits the completion across two transactions: the initiation transaction calls `stampMoneyCommandResource` to write `resource_type` and `resource_id` while the key row stays in progress, and a later transaction calls `completeMoneyCommand` without pointer arguments to write `COMPLETED` and `completed_at` and leave the stored pointer untouched. Payout keeps the one-write shape at prepare: its `execute` hook calls `completeMoneyCommand` with pointer arguments in the initiation transaction, so the row completes before provider submission. Pointer arguments keep the one-write shape: absent arguments leave the pointer columns as they are, and an explicit `null` pair writes a null pointer, the no-op release shape.

A lost insert waits on the row lock — the only row the module ever locks — and then replays through one `replay` hook. The hook absorbs the three stored shapes. A pointer row replays by reading the resource the pointer names. The payout and top-up shape replays by reading on `resource_id` and owner together inside the hook. A completed row without a pointer replays the original no-op result, which is the non-ACTIVE release shape. After the lock, a missing row raises `IDEMPOTENCY_UNAVAILABLE`, because the winner rolled back; a different `request_hash` raises `IDEMPOTENCY_KEY_REUSED`; and a row in progress with no pointer and no completed marker raises `409 IDEMPOTENCY_IN_PROGRESS`. All three are the existing `MoneyDomainError` codes, and the decision adds no code and no HTTP mapping. The result is `{ keyId, result }` and nothing else: it never says whether this run did the work or replayed it, as ADR-0030 requires.

Four Domain Owner rulings all keep current behavior, so the money domain needs no Candidate Rulebook: nothing pinned changes. Admin decisions stay recorded on the Admin action records, not on Money Command rows. Rejections stay unrecorded; the rollback is the record. No sweeper purges expired rows. `409 IDEMPOTENCY_IN_PROGRESS` stays for a key that is in progress with nothing to replay yet.

The storage wall stands: the mechanics are shared, the storage is not. ADR-0009 keeps the money subsystem independent of the Quest model, and ADR-0029 keeps Quest command records in the Quest-owned `quest_command` table. The Money Command protocol serves only `wallet.*` scopes on `wallet_idempotency_keys`. `quest_command` stays Quest-only, and the module never reads or writes it.

The transport wall stands beside it. The Payment Provider Event Inbox (`payment_provider_event_inbox`) owns transport replay for asynchronous external provider webhooks: leasing via `SKIP LOCKED`, attempt counting (0–5), `DEAD_LETTER` handling, and encrypted payload retention. The Money Command protocol owns client-facing synchronous money commands on `wallet.*` scopes (`wallet_idempotency_keys`). The two never meet in one transaction: provider event processing updates Payout state and settles the ledger in its own transaction, while the Wallet idempotency key has been completed since initiation. The Inbox does not fold into `wallet_idempotency_keys` (ADR-0008, ADR-0011, issue #511).

Existing `wallet_idempotency_keys` rows replay identically through the module. The decision adds no column and no migration: a legacy pointer row, a legacy in-progress row, and a legacy completed row without a pointer all read as-is under the one convention above.

Two alternatives lost. One verb that completes inside its own call cannot express the top-up window, which must stay in progress across the provider call and complete in a later transaction. A thin shared helper that only removes the copies leaves the per-caller drift in place — the drift the reconciliation map (#501) deletes.
