## 1. บทนำ

เอกสารนี้สรุปผลการตรวจสอบสัญลักษณ์ BPMN ทั้งหมดที่เป็น "ทางการ" (formal) บนบอร์ด Miro ของ KUQuest พร้อมเทียบกับสถานะปัจจุบันของโค้ดใน repository นี้

เอกสารนี้ตอบคำถามสามข้อ:

1. บนบอร์ดมีไดอะแกรมอะไร อะไรคือ BPMN ทางการ อะไรคือสมุดงาน (Activity Diagram) ฉบับร่าง หรือสำเนาซ้ำ
2. กระบวนการ As-Is เป็นอย่างไร และกฎธุรกิจใดถูกบันทึกว่าเป็นกฎสถานะปัจจุบัน
3. ไดอะแกรมและกฎเหล่านั้นสอดคล้องหรือขัดแย้งกับระบบ `/quest` ใน repository มากน้อยเพียงใด

เอกสารนี้แยกเนื้อหาเป็น: ข้อเท็จจริงที่ยืนยันแล้ว, การอนุมาน, หลักฐานจาก repository, ความขัดแย้ง และคำถามเปิด ทุกข้อค้นพบมีรหัสเสถียร (stable ID) ระดับความรุนแรง และการดำเนินการถัดไปที่จำกัดขอบเขตไว้ที่การทบทวน การขอคำชี้แจง การจัดทำเอกสาร หรือการตรวจสอบยืนยันเท่านั้น

## 2. ขอบเขตและวิธีการ

- **ขอบเขตการให้คะแนน:** เฉพาะไดอะแกรม BPMN ทางการ 5 ชุด ซึ่งใช้ชื่อเรื่องนำหน้าด้วยคำว่า `Ultimate` เรียกในรายงานนี้ว่า D8, D9, D20, D21, D22
- **หลักฐานสนับสนุน:** ไดอะแกรมกิจกรรม (Activity Diagram) สำเนาซ้ำ และฉบับร่าง ใช้เป็นหลักฐานประกอบเท่านั้น **ไม่** ให้คะแนนด้านสัญลักษณ์ BPMN
- **หมายเลข D:** บอร์ดไม่มีป้ายกำกับ `D1`–`D23` อย่างเป็นทางการ หมายเลข D ทั้งหมดในเอกสารนี้เป็น **ป้ายกำกับเชิงอนุมาน** จากลำดับวิดเจ็ตบนบอร์ด **ใช้ Widget ID เป็นคีย์อ้างอิงที่เสถียร** เสมอ
- **จำนวนรายการ:** การตรวจสอบใช้รายการทำงาน (working inventory) 23 รายการ พบวิดเจ็ตตารางกระบวนการขนาดใหญ่ 22 รายการ ในจำนวนนี้ 5 รายการเป็น BPMN ทางการ **D23 ไม่พบวิดเจ็ตที่ตรงกัน** เว้นแต่จะมีหลักฐานใหม่พิสูจน์ได้ **อย่าอ่านว่าบอร์ดมี 23 ไดอะแกรม BPMN**
- **หลักฐาน:** payload ของวัตถุบนบอร์ด (shape/text/image/table object) สรุปภาพเบื้องต้นของแต่ละไดอะแกรม และโค้ด/เอกสารใน repository ณ ต้นไม้ทำงานปัจจุบัน (รวมการเปลี่ยนแปลงที่ยังไม่ commit)

### ข้อจำกัดของหลักฐาน (บันทึกไว้ชัดเจน)

1. **โควตา Miro AI หมด** — `miro_context_get` คืนข้อความว่าองค์กรใช้โควตา Miro AI ครบแล้ว จึงไม่สามเส้นทางของ connector (เส้นเชื่อม) ซ้ำด้วยภาพ ได้สรุปภาพเบื้องต้นและ payload ของวัตถุไว้ก่อนหมดโควตาเท่านั้น
2. **PostgreSQL ในเครื่องไม่พร้อมใช้** — การเชื่อมต่อ `localhost:5432` ถูกปฏิเสธ จึงใช้ schema (`src/database/schema/quest.schema.ts`) และเอกสาร EDR (`docs/db/edr/05-quest.sql`) แทนข้อมูลแถวจริง
3. **ไฟล์อ้างอิงไม่พบ** — `references/bpmn-rules.md` และ `references/professor-feedback.md` ไม่พบใน repository และไม่พบคอมเมนต์บนบอร์ดที่เป็น feedback ของอาจารย์
4. **ไม่มีการแก้ไข Miro** — การตรวจสอบเป็นแบบอ่านอย่างเดียวทั้งหมด

## 5. กฎธุรกิจสถานะปัจจุบันที่บันทึกไว้

รายการต่อไปนี้คือกฎที่บันทึกไว้ระหว่างการตรวจสอบเพื่อใช้ประเมินไดอะแกรม กฎเหล่านี้เป็นการตัดสินใจของทีมกระบวนการ ไม่ได้อนุมานจากรูปทรงของไดอะแกรม เอกสารนี้ไม่ตัดสินว่ากฎใดถูกต้อง

1. FCFS คือชื่อทางธุรกิจของ `NO_CANDIDATE`
2. Join Code ใช้กับ Candidate + GROUP มีวันหมดอายุและสร้างใหม่ได้
3. Candidate + GROUP จบ Team Setup ด้วยการบันทึกทีมที่ครบจำนวนและส่งให้ Hirer เลือก
4. FCFS + GROUP มอบหมาย Worker ทุกคนเมื่อครบจำนวนพอดี แล้วเปิด Work Conversation
5. ต้องได้ความยินยอม (Consent) ก่อนเริ่มงาน
6. Worker กดปุ่มเริ่มทำงานได้หลังเวลาเริ่มเท่านั้น
7. งานฉบับร่าง (Draft) เป็น Message พร้อม Attachment ใน Work Conversation
8. แก้ Draft ต่อได้ตามความเห็นชอบก่อนส่ง Final Proof
9. Final Proof เป็นที่สุด ห้ามแก้ และ Rework ถูกถอดออกจากกฎสถานะปัจจุบัน
10. Hirer เปิด Report Case เมื่อ Worker ไม่มาทำงาน หรือ Final Proof ไม่ผ่าน Quest condition
11. ระบบระงับ (suspend) Quest ระหว่าง Admin พิจารณา Report Case
12. FCFS + GROUP ใช้ Final Proof หนึ่งชุดต่อ Worker หนึ่งคน
13. Candidate + GROUP ใช้ Final Proof หนึ่งชุดจาก Group Leader เท่านั้น
14. การจบ Quest แบบไม่ต้องส่งหลักฐาน (Proof-free) ต้องมีการยืนยันของ Worker ทุกคนที่จำเป็น แล้ว Hirer ยืนยันหนึ่งครั้งตามหลัง
15. Quest ต้องเป็น `COMPLETED` ก่อนเปิด Review
16. Hirer และ Worker รีวิวกันได้ฝั่งละครั้ง ภายในเจ็ดวันหลัง Completed
17. ความผิดฝั่ง Worker: Worker ไม่ได้ Quest Reward, Hirer ได้เงินคืนเต็ม, Quest เป็น Cancelled
18. ความผิดฝั่ง Hirer: Worker ทุกคนได้ Quest Reward เต็ม, Platform Fee เป็นภาระ Hirer, Quest เป็น Completed

## 7. ทะเบียนข้อค้นพบ (Findings)

รูปแบบของแต่ละข้อค้นพบ: รหัส — ชื่อ (ระดับความรุนแรง) / ไดอะแกรมที่กระทบ / หลักฐาน / ข้อเท็จจริงที่สังเกตได้ / การอนุมานหรือความไม่แน่นอน (ถ้ามี) / การดำเนินการถัดไปที่จำกัดขอบเขต การดำเนินการถัดไปทุกรายการเป็นเชิงทบทวน ขอคำชี้แจง จัดทำเอกสาร หรือตรวจสอบยืนยันเท่านั้น

### 7.1 ข้อค้นพบร่วมของไดอะแกรมทางการทั้งหมด

**BPMN-01 — ความสัมพันธ์ของเส้นเชื่อมไม่ตรวจสอบย้อนกลับได้ (medium)** — ไดอะแกรม: D8, D9, D20, D21, D22

- การดำเนินการถัดไป: จัดทำ edge list หรือแหล่งอ้างอิง BPMN ที่ระบุความสัมพันธ์เส้นเชื่อมอย่างตรวจสอบย้อนกลับได้ แล้วให้เจ้าของกระบวนการทบทวนความถูกต้อง

- การดำเนินการถัดไป: ทบทวนและจัดทำทะเบียนชื่อที่ควรมีของ Start/End Event, Gateway และทุกสาขาออก โดยให้เจ้าของกระบวนการยืนยันคำถามของแต่ละ Gateway

## 8. การทำแผนที่กับระบบ `/quest` ปัจจุบัน

ส่วนนี้เป็นภาพระดับธุรกิจ รายละเอียดทางเทคนิคเต็มอยู่ในภาคผนวก A จุดเน้นคือพฤติกรรม Candidate ทีม และการอนุมัติ/การเลือก

### 8.1 ข้อเท็จจริงยืนยันแล้วจากซอร์สโค้ด (repository corroboration)

1. **Candidate + SOLO — การสมัคร:** `createApplication` (`src/modules/quest/quest-candidate.service.ts`) ยอมรับเฉพาะ Quest ที่ `CANDIDATE` + `SOLO` + `QUEST_OPEN` ปฏิเสธ Hirer ที่สมัครเอง จำกัดหนึ่งใบสมัครต่อคนต่อ Quest (UNIQUE `(quest_id, worker_id)`) แก้ `rework_limit` ได้เมื่อยัง `APPLICATION_APPLIED` และถอน (`APPLICATION_WITHDRAWN`) ได้ก่อนการเลือก
2. **Candidate + GROUP — ทีม คำเชิญ และการส่งทีม:** ทีมมีได้เฉพาะ `CANDIDATE` + `GROUP` + `QUEST_OPEN` การสร้างทีมเพิ่ม Leader เป็นสมาชิกแรก (`createTeam`) Leader แก้ชื่อทีม/`rework_limit` ได้เฉพาะขณะ `TEAM_FORMING` (`updateTeam`) เชิญ Member ด้วยคำเชิญในระบบ (`createInvitation`) สมาชิกยอมรับ/ปฏิเสธได้ (`acceptInvitation`/`declineInvitation`) Leader ถอนคำเชิญได้ (`revokeInvitation`) และส่งทีมได้เมื่อ **จำนวนสมาชิกเท่ากับ `headcount` พอดี** (`submitTeam` ตรวจ `members.length !== current.headcount` → `TEAM_HEADCOUNT_MISMATCH`) ทีมที่ส่งแล้วไม่แก้ไขได้ Worker อยู่ทีมเดียวต่อ Quest (`ensureNoMembership`)
3. **อายุคำเชิญและการหมดอายุแบบอะซิงโครนัส:** `expires_at = created_at + 24 ชั่วโมง` การอ่านทาง API **ไม่เปลี่ยน** สถานะคำเชิญ เฉพาะ scheduled worker (`expirePendingQuestTeamInvitations` ใน `quest-lifecycle.worker.ts`) เปลี่ยน `INVITATION_PENDING → INVITATION_EXPIRED` การยอมรับคำเชิญ pending ที่หมดอายุแล้วถูกปฏิเสธด้วย `INVITATION_EXPIRED` (HTTP 409) โดยไม่เปลี่ยนสถานะที่เก็บไว้ (`respondToInvitation` ตรวจ `expiresAt` ก่อนยอมรับ)
4. **การเลือก Candidate → Assignment → Quest เป็น ASSIGNED ภายในธุรกรรมเดียว:** `selectCandidate` ล็อกแถว Quest และ roster (`FOR UPDATE`) ตรวจว่าเป็น Hirer เจ้าของและ Quest ยัง `QUEST_OPEN` เลือกได้เฉพาะ `APPLICATION` กับ SOLO และ `TEAM` (ต้อง `TEAM_SUBMITTED` และจำนวนเท่า headcount) กับ GROUP ทำเครื่องหมายผู้ชนะ `SELECTED` ปฏิเสธ Candidate อื่นที่ยังรอ (`APPLICATION_REJECTED` / `TEAM_REJECTED`) สร้าง `ASSIGNMENT_ACTIVE` หนึ่งรายการต่อ Worker ที่ถูกเลือก เปลี่ยน Quest เป็น `QUEST_ASSIGNED` และเรียก Work Chat membership writer **ในธุรกรรมฐานข้อมูลเดียวกัน** หาก writer ล้มเหลว ทั้งธุรกรรมถูกย้อนกลับ (`WorkChatTransitionError` → HTTP 503 `WORK_CHAT_UNAVAILABLE`)
5. **การเข้าร่วมตรง (NO_CANDIDATE) แยกจาก Candidate:** `joinNoCandidateQuest` (`src/modules/quest/quest-assignment.service.ts`) ยอมรับ Worker หนึ่งคนต่อคำสั่งบน Quest `NO_CANDIDATE` ที่ยัง `QUEST_OPEN` ปฏิเสธ Hirer และ Worker ซ้ำ SOLO เปลี่ยนเป็น `QUEST_ASSIGNED` ทันที GROUP เปลี่ยนเมื่อจำนวน Active ครบ `headcount` พอดี (นับ roster ภายใต้ล็อกแถว Quest เพื่อกันเติมเกินพร้อมกัน) — เส้นทางนี้ไม่สร้างทีมและไม่ผ่านการเลือกของ Hirer
6. **ข้อจำกัดความซ้ำ (uniqueness):** `quest_application` UNIQUE `(quest_id, worker_id)` + partial unique เลือกได้หนึ่งรายการต่อ Quest; `quest_team` partial unique `TEAM_SELECTED` หนึ่งทีมต่อ Quest; `quest_assignment` UNIQUE `(quest_id, worker_id)`; `quest_team_invitation` partial unique คำเชิญ pending หนึ่งรายการต่อ (ทีม, ผู้ถูกเชิญ); ตารางคำสั่งทั้งสาม (`quest_direct_join_commands`, `quest_candidate_selection_commands`, `quest_settlement_commands`) มี `command_id` UNIQUE เพื่อ replay ผลลัพธ์เดิมเมื่อ retry
7. **รันไทม์ปัจจุบัน fail-closed ที่ Work Chat:** ในต้นไม้ซอร์สปัจจุบัน **ไม่มี** จุดใดใน `src/` เรียก `configureQuestWorkChatMembershipWriter` เพื่อติดตั้ง adapter จริง (มีเพียงนิยามฟังก์ชันใน `quest-assignment.service.ts` และการตั้งค่าในไฟล์ทดสอบ) ผลคือขณะรันจริง `joinNoCandidateQuest` และ `selectCandidate` จะโยน `WorkChatTransitionError` และ API ตอบ **503 `WORK_CHAT_UNAVAILABLE`** — ไม่มี Assignment หรือการเลือกใด commit ได้จนกว่า writer จะถูกตั้งค่า นี่คือพฤติกรรมที่ออกแบบไว้ (fail-closed) ตามหัวข้อ ADR 0005
8. **ช่องว่างการทดสอบ:** `tests/modules/quest/quest-assignment.integration.test.ts` ครอบคลุม direct join ครบวงจร (รวม concurrent GROUP join และ rollback เมื่อ Work Chat ปฏิเสธ) แต่ `tests/modules/quest/quest-candidate.integration.test.ts` ครอบคลุมเฉพาะสัญญา HTTP (validation ก่อน auth, ต้องมี Idempotency-Key, เผยแพร่ OpenAPI) — **ธุรกรรม `selectCandidate` (fan-out Assignment, idempotent replay, rollback) ยังไม่มี integration test** และ `configureQuestWorkChatMembershipWriter` ถูกใช้ในไฟล์ทดสอบเพียงสองไฟล์ (assignment และ settlement)
9. **ความขัดแย้งที่ยังคงอยู่ในโค้ด/เอกสาร (ยืนยันด้วยการอ่านไฟล์):** enum `quest_status` ยังมี `QUEST_REWORK` (`quest.contract.ts`, `docs/db/edr/05-quest.sql`), `rework_limit` ยังอยู่บน `quest_application` และ `quest_team`, และ `docs/deprecated/quest-stage-milestones.md` ยังบรรยายทาง `REWORK` — ขัดกับกฎข้อ 9 ที่ถอด Rework ออก (DB-01)

### 8.2 ความเชื่อมโยงกับไดอะแกรม

- ข้อเท็จจริงข้อ 1–5 เทียบกับ D9 (เส้นทาง Candidate), D22 (Team Setup) และกฎข้อ 1–4
- ข้อเท็จจริงข้อ 4 เทียบกับจุดส่งต่อ D22 → D9 และ D9 → D21 (ทีมที่ส่งรอ Hirer เลือก แล้ว Quest เข้าสู่ `ASSIGNED` ก่อนเริ่มงานตาม `start_time`)
- ข้อเท็จจริงข้อ 7 มีผลเชิงปฏิบัติ: ขณะนี้ผู้ใช้จริงยังไปถึงสถานะ `ASSIGNED` ผ่าน API ไม่ได้ทั้งสองเส้นทาง จนกว่า writer จะถูกตั้งค่า — ผู้อ่านเชิงธุรกิจควรทราบว่าไดอะแกรมบนบอร์ดบรรยายกระบวนการเป้าหมาย ไม่ใช่พฤติกรรมรันไทม์ทุกประการ

## 9. ความขัดแย้งระหว่างบอร์ด กฎที่บันทึกไว้ และ repository

ความขัดแย้งต่อไปนี้เป็นการสังเกตจากการอ่านไฟล์ ไม่ใช่ข้อสรุปว่าฝ่ายใดถูกต้อง แต่ละรายการต้องการ "การตัดสินใจเชิงทบทวน" จากเจ้าของกระบวนการ/ผลิตภัณฑ์

**DB-01 — Rework (high):** กฎข้อ 9 ถอด Rework ออกจากกฎปัจจุบัน แต่ `QUEST_REWORK` ยังอยู่ใน `quest_status` (`src/modules/quest/quest.contract.ts`, `docs/db/edr/05-quest.sql`), `rework_limit` ยังอยู่บน `quest_application`/`quest_team`, และ `docs/deprecated/quest-stage-milestones.md` ยังมีทาง `REWORK` ในแผนภาพสถานะ — ต้องตัดสินว่าเป็นข้อมูลสืบทอด (legacy) หรือต้องมีการย้ายโดเมนในภายหลัง

**DB-02 — Join Code (medium):** กฎข้อ 2 ใช้ Join Code บนบอร์ด D22 แต่ schema/EDR ปัจจุบันใช้ `quest_team_invitation` (คำเชิญในระบบ) และไม่มีฟิลด์ Join Code — ต้องยืนยันว่า schema เป็นของเดิม หรือ Join Code เป็นความต้องการพัฒนาต่อ

**DB-03 — เจ้าของ Proof ของทีม (medium):** กฎข้อ 13 กำหนด Leader เท่านั้น แต่ `findOwner` ใน `src/modules/quest/quest-proof.service.ts` อนุญาตสมาชิกทีมที่ยัง Active ใดก็ได้ (ดู APP-09) — ต้องตัดสินว่าจะปรับข้อกำหนดบริการหรือปรับกฎ

**DB-04 — ความยินยอม (medium):** กฎข้อ 5 ใช้ Consent ก่อนเริ่มงาน แต่ EDR บันทึก `QUEST_AWAITING_CONSENT` สำหรับความยินยอมของ Quest Edit **หลังมี Assignment** (BE-175) ทั้งสองเป็นสถานการณ์ต่างกัน — ต้องตัดสินก่อนนำไปใช้ว่าจะแยกสถานะ/กลไกอย่างไร

**DB-05 — เส้นทาง Proof-free (medium):** schema/EDR มี `quest_completion_confirmation` ตรงกับกฎข้อ 14 แต่ D21/D20 ยังไม่แสดงเส้นทางนี้ (ดู QD-05, APP-06) — ต้องทบทวนการแสดงผลในไดอะแกรม

## 10. คำถามเปิดรวบยอด

1. roster ของความยินยอมก่อนเริ่มงานคือ Worker เท่านั้น หรือ Hirer รวม Worker ทุกคน (QS-03)
2. Quest หลาย Worker กลายเป็น `IN_PROGRESS` เมื่อใด หากมีเพียงบางคนกดเริ่มงาน (QD-01)
3. Final Proof ส่งผ่านฟอร์มเฉพาะ Work Conversation หรือทั้งสอง (APP-02, QD-04)
4. อายุ Join Code นานเท่าใด และกฎความปลอดภัยคืออะไร (TEAM-01, TEAM-04)
5. Join Code ที่สร้างใหม่เพิกถอนโค้ดเดิมทั้งหมดหรือไม่ (TEAM-01)
6. สถานะและ SLA ของ Report Case ที่ผู้ใช้เห็นคืออะไร และสัมพันธ์กับข้อพิพาทการจ่ายเงินอย่างไร (QD-03)
7. ฟิลด์ Rework ในฐานข้อมูลจะคงอยู่เป็นข้อมูลสืบทอดหรือไม่ (DB-01)
8. ฐานข้อมูลจะรองรับ Join Code และการส่ง Proof เฉพาะ Leader หรือไม่ (DB-02, DB-03)
9. การทำแผนที่หมายเลข D อย่างเป็นทางการควรใช้ชุดใด — payload บอร์ดมีแต่ Widget ID ไม่มีป้าย D (หัวข้อ 2)
10. มีไดอะแกรม D23 ภายนอกที่ไม่ถูกคืนในรายการวิดเจ็ต 22 รายการหรือไม่ (หัวข้อ 3)
11. คำศัพท์ "Group Leader/Group Member" บนบอร์ดกับ "Team Leader/Team Member" ใน repository ควรรวมเป็นคำเดียวหรือไม่ (หัวข้อ 3)

## 11. ภาคผนวก A — สรุปทางเทคนิคสำหรับทีม `/quest`

### A.1 ทรัพยากร HTTP ที่เกี่ยวข้อง (ยืนยันจากไฟล์ route)

| ทรัพยากร                                                                                                                                                                                  | ไฟล์                                                                                         |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `POST /api/v1/quests/:questId/join`                                                                                                                                                       | `src/modules/quest/quest-assignment.route.ts` (controller: `joinNoCandidateQuestController`) |
| `POST /:questId/applications`, `GET .../applications[/:applicationId]`, `PATCH`, `POST .../withdraw`, `POST .../applications/:applicationId/select`                                       | `src/modules/quest/quest-candidate.route.ts`                                                 |
| `POST /:questId/teams`, `GET/PATCH .../teams/:teamId`, `GET .../members`, `POST .../leave`, `DELETE .../members/:memberId`, `POST .../submit`, `POST .../teams/:teamId/select`            | ไฟล์เดียวกัน                                                                                 |
| `POST/GET .../teams/:teamId/invitations`, `DELETE .../invitations/:invitationId`, `GET /api/v1/quests/invitations[/:invitationId]`, `POST .../invitations/:invitationId/{accept,decline}` | ไฟล์เดียวกัน                                                                                 |
| `POST /:questId/proof`, `GET /:questId/proof`, `POST .../proof/confirm`, `POST .../proof/:proofId/review`                                                                                 | `src/modules/quest/quest-proof.route.ts`                                                     |
| `POST /:questId/cancel`, `POST /:questId/dispute/resolve` (admin)                                                                                                                         | `src/modules/quest/quest-settlement.route.ts`                                                |

- เลือก Candidate ทั้งสอง endpoint ใช้ controller เดียว (`selectCandidateController`) ต้องมี header `Idempotency-Key` (หาย/ว่าง → 400 `IDEMPOTENCY_KEY_REQUIRED`; ใช้ซ้ำต่างคำขอ → 409 `IDEMPOTENCY_KEY_REUSED`) และเรียกผ่าน guard `createQuestIdempotencyKeyGuard('candidate-selection')`
- โค้ดข้อผิดพลาดหลักของการเลือก: `QUEST_NOT_OPEN`, `CANDIDATE_SELECTION_NOT_ALLOWED`, `CANDIDATE_NOT_SELECTABLE`, `TEAM_HEADCOUNT_MISMATCH`, `ASSIGNMENT_ALREADY_EXISTS`, `WORK_CHAT_UNAVAILABLE` (503)
- route ทั้งหมดประกอบใน `src/app.ts` (บรรทัด 47: `.use(questCandidateRoute)`)

### A.2 สัญลักษณ์สำคัญ

- `src/modules/quest/quest.contract.ts` — คลังสถานะทั้งหมด (`questStatus`, `teamStatus`, `applicationStatus`, `assignmentStatus`, `invitationStatuses`); รวม `QUEST_REWORK` ที่ยังไม่ถูกถอด (DB-01)
- `src/modules/quest/quest-candidate.service.ts` — `createApplication`, `createTeam`, `submitTeam`, `createInvitation`, `respondToInvitation`, `selectCandidate` (ธุรกรรมเดียว: ล็อก Quest+roster → สถานะ Candidate → Assignment fan-out → `QUEST_ASSIGNED` → `writer.applyQuestTransition` → บันทึกผลคำสั่ง)
- `src/modules/quest/quest-assignment.service.ts` — `joinNoCandidateQuest` (นับ roster ใต้ `FOR UPDATE`, SOLO→assigned ทันที, GROUP→assigned เมื่อครบ headcount), `configureQuestWorkChatMembershipWriter` / `requireQuestWorkChatMembershipWriter` / `WorkChatTransitionError`
- `src/modules/quest/quest-lifecycle.worker.ts` — `startDueAssignedQuests` (`start_time`), `disputeOverdueQuests` (`due_at` + ตรวจภาระค้าง: ทีมที่เลือกใช้ proof/confirmation ระดับทีม, รายคนใช้ระดับ Worker), `expirePendingQuestTeamInvitations` (24 ชม.), edit-request timeout, `autoApproveDueProofs` (เจ้าของกฎอยู่ที่ `quest-proof.service.ts`: `NO_CANDIDATE` 1 ชม., `CANDIDATE` 2 ชม.)
- `src/modules/quest/quest-proof.service.ts` — `findOwner` (Candidate+GROUP → ทีม `TEAM_SELECTED` ของสมาชิก Active ใดก็ได้; Candidate+SOLO → `APPLICATION_SELECTED`), `submitted_by_user_id` บันทึกผู้กดส่งจริง

### A.3 ช่องว่างที่ควรเข้าแผนทบทวน

1. ไม่มี integration test ของธุรกรรม `selectCandidate` (fan-out, replay, rollback) — ปัจจุบันมีเฉพาะสัญญา HTTP ของ `quest-candidate.integration.test.ts`
2. ไม่มี composition ใน `src/` ติดตั้ง Work Chat writer จริง → รันไทม์ fail-closed (503) จนกว่าจะต่อ adapter (ADR 0005)
3. ความขัดแย้ง DB-01–DB-05 (หัวข้อ 9) แต่ละรายการต้องการการตัดสินใจเชิงทบทวนก่อนเขียนโค้ดเปลี่ยน

## 12. แยกประเภทข้อความ (สรุปความน่าเชื่อถือ)

- **ข้อเท็จจริงที่ยืนยันแล้วจากบอร์ด:** เนื้อหาวัตถุและ Widget ID ในหัวข้อ 3, 4 และทุกช่อง "หลักฐาน" ของข้อค้นพบ
- **การอนุมาน:** หมายเลข D ทั้งหมด, การส่งต่อระหว่างไดอะแกรม (หัวข้อ 4.6), lane Handler (QS-05), ระบบภายนอกที่ไม่ปรากฏ (REG-02, TEAM-04), ความสอดคล้อง Group Leader ↔ Team Leader

- **กฎที่บันทึกไว้:** หัวข้อ 5 เป็นการตัดสินใจของทีมกระบวนการระหว่างการตรวจ ใช้เป็นเกณฑ์เทียบไดอะแกรม ไม่ใช่ข้อเท็จจริงเชิงระบบ
- **ความขัดแย้ง:** หัวข้อ 9
- **คำถามเปิด:** หัวข้อ 10 และคำถามท้ายของแต่ละไดอะแกรมในหัวข้อ 7
