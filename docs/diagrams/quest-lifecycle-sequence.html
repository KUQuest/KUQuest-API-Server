Resolved Quest Lifecycle & Endpoint Interaction

Complete time-ordered interaction flow across Hirer, Worker, Quest API, and Escrow Engine—from Draft creation and Funding Reservation to Proof Submission, Terminal Resolution, and Rating Review.

LIFECYCLE STATES

Quest State Transitions

  • QUEST_DRAFT: Unfunded draft created by Hirer with optimistic concurrency.
  • QUEST_OPEN: Published quest with Escrow reserved in Wallet ledger.
  • QUEST_ASSIGNED: Roster filled (direct join or candidate selected); Work Chat opens.
  • QUEST_IN_PROGRESS: Work phase active following startTime or explicit start.
  • QUEST_COMPLETED: Proof approved or auto-approved; net Reward transferred.
  • QUEST_FAILED: Non-approved proof or missed deadline; 7-day refund hold.

API V2 ENDPOINTS

Related API Routes

  • POST /api/v2/quests: Create new Quest Draft with details and requirements.
  • POST /api/v2/quests/:id/publish: Atomic Funding Reservation and transition to Open.
  • POST .../join or .../apply: FCFS Direct Join or Candidate Application.
  • POST .../select: Hirer selects Candidate/Team to assign the Quest.
  • POST .../proof-submissions/submit: Worker submits proof before dueAt.
  • POST .../review: Hirer review (PROOF_APPROVED or PROOF_NOT_APPROVED).
  • POST /api/v2/quests/:id/reviews: 7-day post-terminal rating and review window.

FINANCIAL INVARIANTS

Escrow & Replay Guarantees

  • Idempotency Replay: All v2 state-changing write operations require Idempotency-Key and replay stored outcomes safely.
  • Atomic Escrow: Funding reservation locks total satang upfront at publish; no unpaid worker exposure.
  • Terminal Immutability: Terminal states (COMPLETED, FAILED, CANCELLED) never reopen; money movement settles atomically.
