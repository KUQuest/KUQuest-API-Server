KUQuest API · v2 Proof Submission

What changes when a Worker sends Proof Submission?

This page traces the POST request from the Worker to the database. It answers which Quest, Assignment, and Proof Submission states change at send time.

Direct answer: the POST changes only the Proof Submission from an unsent draft to PROOF_PENDING. It sets sentAt and locks the Proof Submission. It does not change the Quest or Assignment state at that moment: the Quest stays QUEST_IN_PROGRESS, and the Assignment stays ASSIGNMENT_ACTIVE.

Execution trace

Route and command identity

The route is POST /api/v2/quests/:questId/proof-submissions/:proofSubmissionId/submit. The request must include a non-blank idempotency-key. The controller passes the authenticated Member, Quest ID, Proof Submission ID, and command ID to the service.

Server checks the required submitter

The service locks the Quest row in one database transaction. It requires a v2 Quest with Proof required, state QUEST_IN_PROGRESS, a present and future dueAt, and an authenticated Worker who owns the active Assignment. The draft must belong to that Worker or, for a selected Candidate Group, to the Team Leader.

src/modules/quest/v2/proof/quest-proof-v2.service.ts#L479-L563 · #L1110-L1136

Server checks the draft files

The Proof Submission must still be unsent. It must contain at least one file, and no attached file can have PROOF_FILE_FAILED. A failed check returns an error and leaves the draft unchanged.

src/modules/quest/v2/proof/quest-proof-v2.service.ts#L1537-L1554

Only the Proof Submission row changes

The successful write is:

submissionStatus: 'PROOF_PENDING'
sentAt: now
updatedAt: now

The database constraint treats a non-null status and non-null sentAt as a sent Proof Submission. A later PATCH or DELETE is rejected because the Proof Submission is locked.

HTTP response

The endpoint returns HTTP 200 with the serialized Proof Submission. The important fields are status: "PROOF_PENDING" and an ISO submittedAt. A replay with the same command ID returns the stored command result instead of applying a second write.

State changes at send time

Entity Before After POST Changed?
Proof Submission Unsent draft: status = null, sentAt = null PROOF_PENDING, sentAt = now Yes
Quest QUEST_IN_PROGRESS QUEST_IN_PROGRESS No
Assignment ASSIGNMENT_ACTIVE ASSIGNMENT_ACTIVE No

The Rulebook calls this the Proof Review Window. The Hirer decides the outcome after the Worker sends the Proof Submission.
